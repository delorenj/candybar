# Finite schedules and deletion contract — CAND-51

Status: planning contract; **owner policies OPEN**, implementation gated by [owner-policy card t_7204a764](https://plane.delo.sh/33god/browse/CAND-51/). This companion extends CAP-2, CAP-4, CAP-7, CAP-8 and adds CAP-9..11 in `SPEC.md`; it does not change cron's existing behavior, the [Holocene read contract](holocene-view-contract.md), or reversible [archive/steward behavior](steward-contract.md) except at the explicit seams below. Source: CAND-51 and intake t_200de1d1.

## Definition and wire contract

- API create/update and `candybar.toml` accept **exactly one** schedule variant: `schedule: string` (existing unchanged five-field cron) **or** `dates: string[]` (nonempty local ISO datetimes). An IANA `timezone` defaults to UTC. Validate minute alignment; reject nonzero seconds/fractions, repeated input dates and duplicate resolved UTC instants. Reject entirely past registrations. `fireTime` is always UTC.
- Cron definition objects and schedule rows keep `schedule` and omit `dates`; finite objects omit `schedule`, include `dates` and `timezone`. Update response and stream `definition.changed` must respect the same union. SDKs and manifest parser must not turn missing `schedule` into a required field for dates. Never synthesize a cron string for finite jobs.
- PATCH supplied `schedule` or `dates` replaces the variant atomically; both supplied is invalid, explicit null invalid, neither supplied preserves the variant. Other changes retain existing PATCH behavior. Replace/edit and claim/settlement serialize under a per-candybar DB lock. A failed validation leaves the existing definition/occurrences untouched.
- One shared cron/dates schedule Strategy supplies dispatcher matching, executor backlog, misfire/window/next, skip validation, and CLI display. Cron remains standard five-field and keeps existing Vixie DST/coalescing semantics. Dates cannot silently inherit cron's coalesce-to-latest policy. List, next, window and SSE observe the same UTC fire instants; preserve idempotency by `{candybar_id,fire_time}` across replay. Manual `run` never consumes a date.

## Occurrence lifecycle and cleanup

- Durable `candybar_occurrences` uniquely keyed `(candybar_id, fire_time)` tracks every finite date through claim and terminal settlement. Settled outcomes include completed success/failure and an explicitly recorded skip/overlap or policy-approved missed disposition; **publication, elapsed wall clock, and a pending/running invocation are not terminal**. Allow out-of-order terminal completion. A replay cannot claim/run a settled occurrence twice or erase its disposition.
- Auto-delete is eligible only when **all listed occurrences** are durably settled and no invocation or steward task is queued/running. On restart, the ordinary tick/daemon recovery path must re-evaluate eligible definitions, not rely on an in-memory completion callback. Claim, edit, delete and settlement use a per-candybar DB lock so a late claim cannot race physical removal. Manual execution cannot satisfy the finite set. An exhausted paused definition follows Jarad's answer, not a default invented here.
- Existing `skips` and dispatcher/executor coalescing behavior remain for cron. For finite jobs the owner must select missed, pause, operator skip and overlap dispositions before coding: never equate "missed" with "settled" without a durable fact.

## Real deletion and historical identity

- `DELETE /candybars/{id}`: 204 on a successful deletion and repeat of a **known-deleted UUID**, 404 on a never-known UUID; 409 when an invocation or steward task remains active/queued. No force/cancel flag. CLI `candybar delete NAME|ID` resolves NAME against the active inventory and deletes the resulting UUID; history accepts the deleted UUID. A reused name creates a new UUID and never aliases old history. Do not implement deletion as `enabled=false` or `archived=true`: archive stays reversible, deletion physically removes the active definition.
- Introduce `candybar_records` as durable identity/tombstone for known UUIDs, distinct from active `candybars`. Repoint `invocations`, historical skips/occurrences and steward task FK paths away from cascading active-definition deletion to the record, retaining original UUID, history, idempotency/dedupe keys, existing retention, and lookup by invocation ID. Drop `ON DELETE CASCADE` to the active definition for history. Historical profile handling must not cascade run/task history; no new purge policy. History by UUID must not require an active definition; **no new history browser endpoint** is required.
- One registry delete operation handles manual and auto-delete. Under the same DB transaction and per-candybar lock: check active work, remove active definition, persist durable deletion identity and a stable-ID deletion-event outbox entry. Commit before publishing. At-least-once delivery/retry uses existing daemon/tick event paths, not a new timer or private loop; stable event ID lets consumers dedupe. A crash after commit but before publish is recoverable; no deletion fact for a rolled-back deletion. Late queued invoke/steward commands for known-deleted UUIDs are suppressed, not executed or reported as unknown. Concurrent repeated DELETE resolves to 204.
- Bloodbank governance card `t_ff84ad7e` owns the canonical deletion fact vocabulary/schema and finite-capable event revision **before emission**. Preserve unchanged cron v1 payloads and closed created v1 schema; never manufacture a type locally or weaken the schema. This bounded deletion outbox does not imply rewriting every API mutation to an outbox.
- SSE event-first overlay must remove (or invalidate/refetch) deleted definitions and rows without resurrecting them; coordinate a canonical deletion signal at the API/SSE boundary with Bloodbank approval. Existing archived view remains separate.

## Owner-policy gates — do not treat proposals as decisions

1. Mixed past/future dates: reject the whole input, or accept future entries while durably recording past skips? All-past registration rejected either way.
2. Downtime/executor-backlog missed dates: skip/settle or run each late once? On pause, settle elapsed dates immediately or only on resume; may an exhausted paused definition delete before resume?
3. DST gaps/folds for local ISO inputs: reject nonexistent/ambiguous wall times or define exact gap and fold mapping? No silent shift or duplication.
4. Edit/terminal control: may claimed/settled dates change, which future dates may replace them, and may timezone change after a claim? Which failure, operator skip, overlap, and pause dispositions settle an occurrence? Manual run never consumes one.

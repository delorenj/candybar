- source_spec: `_bmad-output/implementation-artifacts/spec-3-1-memory-peak-and-average-cpu-load-per-invocation.md`
  summary: The executor moves a child into its cgroup scope only after spawn. Memory charged before that move (interpreter or runtime startup, about 10 MB for Python) is never counted, and a sub-millisecond job exits before it joins, so it meters 0. Live `deploy-smoke` rows read 0 for this reason.
  evidence: Real and observed. The live `deploy-smoke` write to cgroup.procs failed with ESRCH. The 64 MiB canary reads 64.2 MiB even though the interpreter baseline is about 10 MB, because cgroup v2 never migrates existing charges. Story 3.1's frozen intent rules out a pre-exec join. Closing the gap needs the child to join before exec, either through a `preexec_fn` that writes `0` to an fd held open on the scope's cgroup.procs (fork in a multi-threaded process) or through clone3 CLONE_INTO_CGROUP via a small native helper. Either choice needs a human decision on the tradeoff.
  evidence (independent Epic 3 review, 2026-10-26): the window is about 20 ms, not sub-millisecond, and the affected set is much larger than `deploy-smoke`. Inside the live container, the `cgroup.procs` write in `_enter_scope` itself blocks for about 20 ms in roughly 1 run in 7: the migration takes `cgroup_threadgroup_rwsem` for write, which is a percpu rwsem waiting on an RCU grace period, and the cgroup2 mount has no `favordynmods`. Spawn returns in 0.3 ms with the child in state R. When the write finally lands, the 17–20 ms node job is already exiting, so the kernel silently skips it (PF_EXITING). The write still succeeds, so the run reports `scoped=True` with an empty `cgroup.procs` and meters 0/0. Evidence: an instrumented probe over 60 `hello-node` runs gave 8 runs with join_ms 19–28, `procs: []`, peak 0 and cpu 0. About 30% of live `hello-node` rows (06:00–13:55 UTC) read memory 0. The same write also blocks the daemon's event loop for that long. Implications for the fix: a `preexec_fn` write would charge about 20 ms to the child instead (correct, but slower). clone3 `CLONE_INTO_CGROUP` takes the rwsem only for read on fork, which avoids the wait. Remounting with `favordynmods` would change the host's shared cgroup2 superblock, so it is not a container-local option.
